# 08. Firebase, Services, and Permissions

## Firebase setup

Firebase configuration should be centralized in `src/config/firebase.ts`.

Expected exports:

```ts
export const firebaseApp = initializeApp(firebaseConfig)
export const auth = getAuth(firebaseApp)
export const db = getFirestore(firebaseApp)
export const storage = getStorage(firebaseApp)
```

Environment variables should use the `VITE_` prefix.

## Firestore access pattern

Use service files for every domain.

Example:

```txt
src/services/users.service.ts
src/services/programs.service.ts
src/services/reports.service.ts
```

Each service should expose clean functions:

- `list`
- `getById`
- `create`
- `update`
- `remove` or `archive`
- `subscribe`

## Real-time data

Prefer Firestore `onSnapshot` subscriptions where page data must stay live.

Examples:

- Dashboards.
- Task lists.
- Approval queues.
- Live reports.
- Notifications.

Use one-time reads where real-time updates are not required.

## Permission model

Role-based access must be centralized.

The same permission logic must control:

- Route access.
- Menu visibility.
- Page action buttons.
- Service function permission checks.
- Agent actions.

Do not scatter role checks randomly inside JSX.

## Roles

Initial platform roles:

- `systemadmin`
- `director`
- `projectadmin`
- `operations`
- `consultant`
- `incubatee`

Role labels must be translated in the UI.

## Route permissions

Each route should include `allowedRoles`.

Menus should be generated by filtering routes against the current user's role.

## Intervention assignment data model

The active intervention assignment workflow uses these Firestore collections:

- `assignedInterventions`: one document per participant/intervention assignment. Required routing fields include `companyCode`, `participantId`, `interventionId`, `interventionTitle`, `beneficiaryName`, `type` (`singular` or `grouped`), `assigneeId`, `assigneeName`, `assigneeEmail`, `assigneeType`, `status`, `assigneeStatus`, `incubateeStatus`, `assigneeCompletionStatus`, `incubateeCompletionStatus`, `progress`, `implementationDate`, `dueDate`, `createdAt`, `updatedAt`, and optional `groupId`, `areaOfSupport`, `targetType`, `targetValue`, `targetMetric`, `timeSpent`, `feedback`, `declineReason`, and `reassignmentHistory`.
- `assignees`: assignable delivery-owner records keyed by company. Expected fields are `companyCode`, `name`, `email`, `role`, and optional `uid`, `active`, `departmentId`, and `programIds`. If this collection is empty, the assignment page falls back to `users` with assignable roles.
- `systemSettings`: global or company-specific settings documents. Intervention pages read `assignmentModel` (`ops_assign_consultant` or `consultant_self_assign`), `smeDivisionModel`, and `consultantLabel`.
- `companyAgentSettings`: one document per company. System administrators write `enabledAgentIds`; operations reads this list when configuring intervention delivery.
- `agentWorkRuns`: one document per agent-delivered assignment. Stores the agent draft, template metadata, execution status, and review audit trail. Incubatees may write only their assigned work; operations and assigned reviewers may read and review company-scoped records.
- `notifications`: assignment workflow notifications with `companyCode`, `participantId`, `interventionId`, `interventionTitle`, `type`, `recipientRoles`, localized/user-role `message`, `createdAt`, and `readBy`.

Supporting reads come from `applications`, `participants`, and `users`. Applications must expose accepted growth-plan data through `applicationStatus`, `companyCode`, `participantId`, `beneficiaryName`, `programName`, and `interventions.required` plus `interventions.confirmedBy.operations` and `interventions.confirmedBy.incubatee`.

Operations users can see both assignment management and assigned-intervention tracking. Consultants can always see assigned-intervention tracking through `track_interventions`; consultants only see assignment management when their resolved permissions include `assign_interventions`.

## Service permission guard

Services or calling hooks should validate that the user can perform the requested action.

For example:

```txt
Can current user create this record?
Can current user update this status?
Can current user archive this item?
```

## Data quality rules

- Missing required fields should be treated as data issues.
- Do not silently hide bad records unless there is a clear UX reason.
- Show user-friendly warnings where useful.
- Keep audit fields such as `createdAt`, `updatedAt`, `createdBy`, and `updatedBy` where practical.

## Storage rules

When uploading files:

- Validate file type.
- Validate file size.
- Store metadata in Firestore.
- Do not expose raw storage paths unnecessarily.
- Show human-friendly file names.
